# macOS password-backed private OTLP transport

This optional helper does not install or enable the plugin. Configure only after deployment approval.

`vault_tunnel.py` is a foreground process suitable for a user LaunchAgent with `KeepAlive`, `RunAtLoad`, and `ThrottleInterval: 30`. It execs SSH, binds **127.0.0.1 only**, enforces the existing known host key, disables SSH public-key and connection multiplexing, and uses SSH keepalives plus `ExitOnForwardFailure`. The remote end of the forward is the explicitly configured `remote_host:remote_port` pair (normally the remote host's own LAN interface and its datalake HTTP port, not remote loopback). Traffic from the local endpoint crosses the network encrypted inside SSH; the remote hop to its own interface does not traverse the LAN.

Configuration is a JSON file with nonsecret keys `session`, `bw`, `item`, `host`, `port`, `askpass`, `remote_host`, `remote_port`. `host`/`port` select the SSH server and the local loopback port; `remote_host`/`remote_port` select the forward destination (hostnames: letters/digits/dot/hyphen only, no `:`/`@`/`/`/whitespace/leading `-`; ports: integers 1–65535). Untrusted configuration cannot inject SSH `-L` grammar. There is no hardcoded destination or private fallback: a missing `remote_host`/`remote_port` fails closed. The `session` path points to an **existing** owner-only Vaultwarden session file. Never put the session token or SSH password in settings, plist, environment, logs, command arguments, or a second durable secret file. The askpass executable invokes this same helper with `--config PATH --askpass`; only SSH receives its stdout. The vault session is loaded only into the short-lived BW child process. No extra session token is created.

The deployed service name is `ai.hermes.datalake-otlp-tunnel` and its LaunchAgent is `$HOME/Library/LaunchAgents/ai.hermes.datalake-otlp-tunnel.plist`. The plugin endpoint is `http://127.0.0.1:<port>/v1/traces` with the configured local `port` (example `24418`). Plugin ingress credentials remain a separate owner-only `$HERMES_HOME/usage-otel.credentials.json` file.

LaunchAgent maintenance must be performed from an ordinary user shell outside the supervised Hermes gateway if its runtime blocks `launchctl bootstrap`. Do not work around that guard with another launchctl verb, indirect execution, or terminating the gateway. Independent plugin observer activation uses `hermes plugins enable datalake-usage` and native hot reload; it requires no gateway restart.

Verify the exact service with `launchctl print gui/$(id -u)/ai.hermes.datalake-otlp-tunnel`, local listening address with `lsof -nP -iTCP:<port> -sTCP:LISTEN` (using the configured local `port`, example `24418`), and an authenticated harmless GET (405 proves auth passed; 401 means credentials failed). Do not print the auth header. A running SSH process or bound port alone does not prove upstream forwarding works.

Rollback: disable the plugin through `hermes plugins disable datalake-usage` (hot reload), then boot out only this independent tunnel job from the ordinary user shell. Preserve the private outbox for retry and delivered-identity tombstones. Do not delete Hermes state.db or restart the gateway. A stale/expired existing vault session will prevent reconnect; renew it using the user's established unlock workflow, never by asking for secrets in chat.
